0先讲四句话

会上如果只记四件事，记这四件。

问题答案
系统跑在哪 生产服务器 10.128.85.133 上两个 Docker 世界：业务编排（API + PostgreSQL）和 模型池（35B / BGE）；客户端是装在办公电脑上的桌面程序，默认连 http://10.128.85.133:8000。
代码怎么分 后端 server/app 按 接口层 → 应用层 → 领域层 → 基础设施层 四层切，横切 core；桌面端 desktop 按 15 个功能页切。业务新增只动应用层 + 接口层，不碰技术实现。
模型怎么用 只有一套在线模型：35B（:8010，占 2 卡），文本、视觉、长文三条链路全指向它；向量化走 bge-m3（:8006）。PPT 的 9B 栈已退出正式链路，但容器还在占卡。
脚本在哪 生产权威脚本全在 deploy/：deploy_latest.sh 负责部署，production.docker-compose.yml + model-pool/docker-compose.yml 负责编排。仓库根目录那批 start_all.sh / start_services.sh 是 14B 裸进程时代的遗留，已不可用。

1运行时拓扑：谁在跑、跑在哪台机器

这张图回答「点一下按钮，请求经过了哪几个进程」。注意模型不在 API 容器里，是宿主机上独立的一套 Docker。

图 1｜部署视图。绿色区是模型池，和业务编排是两套独立 compose，互不 restart 牵连。

会上要强调的一点：业务容器里没有模型。模型是宿主机上单独跑的 vllm 服务，API 只通过 HTTP 调它。所以「重启后端」不会影响模型，「模型挂了」也不会让后端进程退出——只会让 AI 功能超时。

2代码架构：四层，一条依赖方向

后端是单体，但内部严格分层。判断一段代码该写在哪，看它「碰什么」：碰 HTTP 去 interfaces，碰业务流程去 application，碰专业规则去 domain，碰数据库/模型/文件去 infrastructure。

图 2｜代码分层。虚线箭头表示依赖倒置：基础设施实现应用层定义的端口，领域层谁都不依赖。

一句话判断法：新功能加在哪一层，看它最外侧碰什么。要新增一个「公文格式检查项」——规则进 domain/，流程进 application/format_check/，开接口进 interfaces/format_check.py，三处都不用改别的模块。

3模型架构：一套 35B，四套网关，8 张卡

这里最容易讲乱。抓住一句：网关有四个，模型只有一个。四套网关只是四种参数策略（超时、温度、上下文、是否带图），终点都是同一个 :8010。

图 3｜模型架构。左侧四套网关 + 一条 RAG 链路，中间是实际的服务实例，右侧是卡位占用。

模型相关环境变量（生产 .env）

变量当前应填作用

MODEL_MAX_CONCURRENCY4网关侧并发闸门，超了排队而不是打爆模型
