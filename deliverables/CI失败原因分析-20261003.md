## 一、结论速览

CI 一直失败**不是环境问题，也不是依赖问题**，而是**一次不完整的重构**：P0 安全整改删除了 HTTP 端点，但没有同步更新依赖该端点的测试。

| 项 | 失败时 | 修复后 |
|----|--------|--------|
| 测试结果 | `2 failed, 269 passed, 150 errors` | **`421 passed, 0 failed`** |
| 根因类别 | 测试与产品代码脱节（3 类） | — |

**关键证据**：本地用与 CI 完全相同的环境变量复现，得到一致的失败集：
```bash
cd server && AI_PROVIDER=mock EMBEDDING_PROVIDER=mock PYTHONPATH=. \
```

## 二、根因一：删除 HTTP 端点后测试未同步（150 errors）

### 发生了什么

评审报告 P0-3 判定「`/auth/register-first` 无令牌可被抢注 administrator」，整改方案是**删除该HTTP 端点**，改为部署时在服务器本地执行：

```bash
python -m scripts.create_admin
```

对应提交 `b160b0d` ~ `5760af3`、`4d83905`。`app/interfaces/auth.py` 现在的全部端点只剩 4 个：

```
POST /auth/login
POST /auth/change-password
POST /auth/register
GET  /auth/me
```

### 为什么导致大面积失败

测试套件里 9 个模块沿用同一套兜底写法：**先打 `register-first` 抢注，失败再查库直接签 token**。

```python
r = client.post(f"{BASE}/auth/register-first", json={...})
if r.status_code == 200:
    return r.json()["access_token"]
# 兜底：查库里任意 developer/admin，签发 token
row = db.scalar(select(UserModel).where(
    UserModel.role.in_(("developer", "admin"))))
assert row is not None, "库中没有可用的系统管理员账号"
```

端点删除后，第一步永远 404，全部落到兜底分支。而兜底分支的前提是「库里已经有别人建好的管理员」——**但每个测试模块的库是本模块独有的空库**（`conftest.py` 的 `_isolate_database_per_module` 为每个模块建独立 SQLite），于是断言集体失败：

```
AssertionError: 库中没有可用的系统管理员账号
```

**受影响的 9 个模块及其原本注册的用户名**：

| 模块 | 期望用户名 | 是否有兜底分支 |
|------|-----------|--------------|
| `test_department_permissions.py` | `developer` | **无**（直接解包 `.json()["access_token"]`） |
| `test_knowledge_route_order.py` | `kbroutedev` | 有 |
| `test_password_policy.py` | `pwddev` | 有 |
| `test_ppt_agent_jobs.py` | `jobdev` | 有（5 级兜底） |
| `test_ppt_kb_rag.py` | `kbdev` | 有 |
| `test_ppt_preview_degrade.py` | `pptprevdev` | 有 |
| `test_ppt_workbench.py` | `pptdev` | 有 |
| `test_timezone.py` | `tzadmin` | 有 |
| `test_user_preferences.py` | `prefdev` | 有 |

其中 `test_department_permissions.py` 因为没有兜底分支，`register-first` 返回 404 的响应体被直接 `.json()["access_token"]` 解包，抛 `KeyError`，是该模块 37 个用例全挂的直接原因。修复时改为用预置的 `developer` 账号登录（唯一需要改测试文件的一处，其余 8 个靠种子账号兜住）。

### 修复方式（已实施）

**没有逐个改9 个测试文件**，而是在 `tests/conftest.py` 的模块级 fixture 里统一补种子账号——这些兜底逻辑本就能工作，只是缺一个可查的管理员。

```python
_SEED_USERNAMES = {
    "test_department_permissions": "developer",
    "test_knowledge_route_order": "kbroutedev",
    # ... 共 9 条
}
_SEED_PASSWORD = "Passw0rd!2026"

def _seed_developer(module_name: str) -> None:
    username = _SEED_USERNAMES.get(module_name, "seedadmin")
    service = AuthService(SqlAlchemyUserRepository(db))
    if service.is_first_user():
        service.register_first(username, f"{username}@test.local",
                               _SEED_PASSWORD, real_name="系统管理员")
```

走**服务层 `AuthService.register_first`** 而非 HTTP：它才是被测的正式入口（`scripts/create_admin` 调的就是它），也就不再依赖被删掉的路由。

**为什么种子用户名必须与各模块原先注册的完全一致**：见根因二。

## 三、根因二：登录限流器把正常用例误伤（连锁放大）
这是修复根因一之后**暴露出来的第二个问题**，也是最容易被误判为「改完还是不行」的地方。

### 发生了什么

P0-2 整改新增了登录限流器 `app/application/identity/login_limiter.py`（提交 `b160b0d`）：

- 策略：同一 IP 或同一用户名 **10 分钟内失败 5 次 → 锁定 15 分钟**
- 状态：**进程级全局单例**，跨测试模块累积
- 已有 `reset()` 方法，注释写明「Test helper」

### 为什么误伤

`TestClient` 发出的请求**来源 IP 全部相同**（testclient 不走真实 socket）。一旦某个模块连续 5 次登录失败：

1. 该IP 桶被锁定 15 分钟
2. **同一进程内所有后续模块的所有登录请求全部 429**
3. 表现为 `KeyError: 'access_token'`——因为登录响应体里根本没有这个字段

实测事件流（修复前，追踪 `login_rate_limiter` 调用）：

```
('check-OK', 'jobdev')
('FAIL',    'jobdev')      ← 首次失败：库里没有 jobdev
('check-OK', 'jobdev')
('FAIL',    'jobdev')
...共 5 次...
('429', 'jobdev',   '登录尝试过多，请 899 秒后再试')
('429', 'jobother', '登录尝试过多，请 897 秒后再试')   ← 另一个账号被连带
```

这解释了为什么「单文件跑全绿、全量跑挂」：

```bash
pytest tests/test_ppt_workbench.py              # 44 passed
pytest tests/test_ppt_agent_jobs.py tests/test_ppt_workbench.py
# → 1 failed, 40 errors
```

### 修复方式（已实施，两处）

**① 按模块重置限流器**（`conftest.py`）

```python
from app.application.identity.login_limiter import login_rate_limiter
login_rate_limiter.reset()
_seed_developer(request.module.__name__)
```

限流逻辑本身的正确性由 `tests/test_delivery_p0_security.py` 单独覆盖，不依赖全量套件跑通。

**② 让种子账号一次登录成功**（关键）

只做① 会剩 1 个 failure：种子账号叫 `seedadmin`，而 `test_ppt_agent_jobs` 的兜底逻辑尝试登录的是 `jobdev` —— 账号不存在，登录失败 5 次照样把 IP 桶打满。

所以 `_SEED_USERNAMES` 按模块名映射到**各模块原本期望的用户名**，密码统一用各模块共用的 `Passw0rd!2026`，使兜底分支第一次就成功。

## 四、根因三：FastAPI 版本差异导致路由断言失效（2 failed）

这是与前两项**性质不同**的失败，与 register-first 无关。

### 现象

```
FAILED tests/test_delivery_p0_security.py::test_bootstrap_http_routes_are_removed
FAILED tests/test_first_admin_no_forced_change.py::test_first_admin_bootstrap_is_not_exposed_over_http
    AttributeError: '_IncludedRouter' object has no attribute 'path'
```

### 原因

这两个是新写的 P0 安全测试，用遍历路由表的方式断言「某些端点已删除」：

```python
paths = {route.path for route in create_app().routes}   # ← 这里
```

但 CI 安装的是 `fastapi==0.139.2`，新版 FastAPI 把子路由包进了 `_IncludedRouter` 对象，**`route.path` 不再稳定存在**，遍历即抛 `AttributeError`。

（本地环境是 `fastapi 0.141.1`，同样失败——这不是本地与CI 的差异，是版本都偏高。）

### 修复方式（已实施）

改用 OpenAPI 路径表，这是跨版本稳定的官方接口：

```python
# 用 OpenAPI 路径表而不是遍历 app.routes：新版 FastAPI 把子路由包进
# _IncludedRouter，route.path 不再稳定存在，遍历会抛 AttributeError。
paths = set(create_app().openapi()["paths"])
```

已验证三条断言仍成立且有意义：

```
/api/v1/files/{attachment_id} in openapi: True← 新增的鉴权下载路由在
/uploads in openapi:              False    ← 匿名挂载已彻底移除（无任何 Mount 残留）
```

## 五、排除的误判：依赖不是原因

排查中曾一度怀疑 `requirements-server.txt` 的版本钉死在 Linux 上装不上（沙箱 pip 代理返回过期索引，误报 `pymupdf==1.28.2`、`faiss-cpu==1.14.3` 不存在）。

**用 PyPI JSON API 逐个核验后撤回该结论**——48 个钉死版本**全部真实存在**，且二进制包都有对应 manylinux wheel：

| 包 | 版本 | linux wheel |
|----|------|------------|
| pymupdf | 1.28.2 | ✓ 4个 |
| faiss-cpu | 1.14.3 | ✓ 4 个 |
| numpy / scipy / pillow / lxml | — | ✓ 均有 |
| bcrypt / cryptography | 5.0.0 / 49.0.0 | ✓ 46/ 37 个 |

`desktop-compile` job 的 Gradle 配置与 wrapper 文件也均正常入库（`gradle-wrapper.jar` 在库、`gradlew` 权限 100755）。

**教训**：CI 依赖问题要用 PyPI 官方 API 核对，不要信本地 pip 代理的索引。

## 七、遗留建议

| # | 事项 | 说明 |
|---|------|------|
| 1 | 9 个测试文件仍保留失效的 `register-first` 调用 | 现在靠种子账号兜住，能跑但属**死代码**。建议后续清理成直接依赖种子，避免误导 |
| 2 | 限流器按 IP 锁定对 `TestClient` 不友好 | 已用按模块 reset 缓解。将来若加并发测试，需给 TestClient 构造可区分的 client host |
| 3 | 缺少 pre-commit / 本地全量校验 | 本次问题本质是「本地没跑全量就 push」。建议 push 前强制跑一次全量 pytest |
| 4 | `desktop-compile` 未覆盖打包 | 当前只编译不打包，`.iss` 语法错误、版本号不同步等问题要到交付前才暴露 |
