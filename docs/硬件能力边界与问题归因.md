# 云法智办平台 · 性能与能力边界说明

**用途**：与何总（服务器/硬件厂商）及领导沟通会 — 明确平台各项体验瓶颈的根因归属，避免把**硬件能力边界**误判为**软件实现缺陷**。  
**口径原则**：以下事实均来自当前生产部署配置与生产环境核实（2026-10 核实），可现场对配置、对日志，不靠主观判断。

---

## 一、结论先行

当前平台在 **生成速度、模型微调/训练、单模型规模上限** 上的瓶颈，根因是部署硬件 **8× 昇腾 310P3 推理卡** 的能力边界，**非后端/前端实现缺陷**。在现有硬件形态下，软件侧已采用该平台可行的最优部署架构（单卡满载跑 14B、独立 9B 跑 PPT、推理侧已做 RAG 降幻觉与质量门拦截）。

> 表述口径："这些不是我们没做，是当前给到的推理卡的能力上限。要跨过这条线，属于资源/采购决策，我们能给出明确的技术测算。"

## 三、常见问题的硬件归因（核心）

| # | 现象 / 用户感受                | 根因                                                  | 是否硬件限制      | 软件侧已做的应对                            |
| - | ------------------------ | --------------------------------------------------- | ----------- | ----------------------------------- |
| 1 | 公文/问答生成偏慢                | 14B 在单芯片以 TP=1 推理，无跨卡张量并行，单卡吞吐即天花板                  | **是（主因）**   | 流式输出、超时恢复、并行检索前置                    |
| 2 | PPT 出稿慢（1页≈100s、2页≈6min） | 含 9B 生成 + 渲染链路，单实例推理                                | **是**       | 异步任务、进度中性提示、断点续跑                    |
| 3 | 不能按业务数据微调/训练             | 310P 是推理卡，无训练能力；训练须 910 系列                          | **是**       | 已设计**训推解耦**：本地攒数据 → 外训 → adapter 回灌 |
| 4 | 模型"不够聪明"/答非所问            | 14B 是单卡(43GB)能稳定跑的最大密集模型（FP16 ~28GB）；32B 密集(~64GB)需双卡 TP=2 且显存紧张，MoE 真实主流型号 **Qwen3.6-35B-A3B**（35B 总/3B 激活/256 专家）。**BF16 原版(~70GB) 必须 910B（Atlas 800 A2，64GB HBM×4、TP=4）**；但 **W8A8 量化版(`Eco-Tech/Qwen3.6-35B-A3B-w8a8`, ~35GB) 在 310P 的 `v0.23.0-310p` 上官方已验证可跑**（CANN 9.1.0 + 多卡 TP，无需升级镜像），建议 **TP=4**（TP=2 KV Cache 极限易 OOM，官方参考 TP=8），占 4 卡须与生产错峰；310P 必加 `--enforce-eager` + `--mamba-ssm-cache-dtype float16` + `--no-enable-prefix-caching`。35B+ 密集(BF16)在 8 卡总量下不现实 | **是（规模上限）** | RAG 检索溯源 + 拒答阈值 + 质量门拦截硬伤           |
| 5 | "宣传说支持多卡，为何没加速"          | 华为官方（vLLM-Ascend 有 310p 专属镜像+Atlas 300I 教程、MindIE 默认 TP）**支持** 310P 多卡 TP，仓库也实测跑过 TP=2 副本；但 310P 的 LPDDR4X 带宽与 HCCL 延迟致多卡 TP 效率低（社区实测 32B 双卡仅~9 tok/s），故主实例仍单卡 TP=1 | **是（卡预算+效率约束）** | 多实例 / TP=2 副本已在工具链就绪（提升并发或单请求算力） |

> 诚实说明：软件侧仍有优化空间（批处理、KV cache、提示词精简），但**边际收益有限**，无法突破硬件吞吐上限。把单请求延迟压下来，本质需要更高吞吐硬件或多卡 TP 架构。

## 四、硬件能力边界（明确"能"与"不能"）

**在 310P 上能做的：**

- 大模型推理（14B 单卡稳定）、多实例数据并行（提升并发）
- LoRA 适配器推理（vLLM-Ascend 支持，实验性），推荐训后 merge 进基座

**在 310P 上不能做的（须换硬件）：**

- 大模型训练 / 微调（需 910 系列）
- 单实例跨卡 TP=2 可行但占 2 卡；8 卡需同时供 14B+9B，靠 TP 扩并发空间有限（要大幅提速需增卡 / 换 910）
- 在单卡稳定跑 >14B 的大模型

---

## 五、已落地的工程应对（证明非"躺平"）

- **训推解耦方案**：数据在此沉淀 → 外训 → adapter 回灌，基座锁定生产 Qwen2.5-14B
- **受限自主修复**：质量门发现硬伤后规则优先 / 模型兜底三级决策，减少人工返工
- **RAG 溯源 + 质量门**：抑制幻觉、拦截文种错 / 发文字号残留等确定性硬伤（D 级拒保存）
- **稳定性**：运行超时自动 `running→interrupted` 可续跑；智能体起草/流式/恢复全程留痕
- **前缀缓存（prefix caching）**：14B/9B 工具链已开启并附验收脚本 `verify-prefix-caching.py`，复用公文助手稳定系统前缀 KV，降低同类请求首 token 时延——属待生产重建验证项
- 当前版本（终版 10.19）回归测试 **937 passed**，桌面端编译通过

## 六、若要突破边界，需要的资源（把议题交回硬件/采购侧）

| 想解决什么        | 需要什么资源                |
| ------------ | --------------------- |
| 想训练/微调自己的模型  | 910 系列训练卡（或外部训练资源）    |
| 想大幅降低单请求延迟   | 支持多卡 TP 的硬件架构，或更高单卡吞吐 |
| 想提升并发不被单请求拖慢 | 多实例数据并行（当前硬件即可，已规划）   |

## 七、会中应答话术（防御但不甩锅，留有余地）

- **"为什么这么慢？"**  
  → "14B 现在是单卡在跑，没有跨卡并行，这是 310P 推理卡的物理上限；我们可以评估多实例或换硬件来提速。"
- **"为什么不能训练？"**  
  → "这套卡是推理卡，训练要 910。我们已经把训推解耦方案设计好了，拿到训练资源就能跑。"
- **"是不是你们代码有问题？"**  
  → "可以先对一下具体现象和案例，我回去拉日志核实；从架构看，当前部署是这套硬件下的最优形态。"
- **被问倒 / 没数据：**  
  → "这个我记下来，回去核实清楚后给您答复。"（不说"我不知道"）
